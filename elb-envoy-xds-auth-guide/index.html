ELB for Envoy → xDS 서버 연결, 인증·인가와 보안 그룹 가이드

2026-11-27 · 근거: AWS 공개 문서, elb-envoy-remote-infra-provider v1.0.0, 로컬 Envoy 1.40.0 재현 · 상세 글 blog.atomai.click/elb-envoy-istio-gateway/#xds-auth

이 문서는 AWS 공개 문서와 작성자의 로컬 재현을 바탕으로 한 작성자의 권장안이며, AWS의 공식 보안 권고나 지원 범위를 나타내지 않습니다. 관리형 프록시에서 직접 측정하지 않은 항목은 마지막 "검증 범위"에 적었습니다.

질문별 답

  1. ELB for Envoy → xDS 연결의 인증·인가는 어떻게 하나요? 인증은 설정 아카이브(configurationArchive)에 넣은 클라이언트 인증서로 mTLS를 합니다. 관리형 프록시에는 서비스 계정 토큰 같은 수단이 없어, 첫 자격 증명은 아카이브로 넣을 수밖에 없습니다. AWS의 EKS 통합도 같은 방식으로 Envoy Gateway에 연결합니다. 인가는 xDS 서버가 인증서 SAN과 node.cluster를 짝지어 합니다(3절).
  2. 아카이브에 정적 키를 넣는 게 권장되나요? 정적 공유 키(bearer 토큰)는 권하지 않습니다. 아카이브에 비밀 값을 넣는 일 자체는 피할 수 없으므로, 프록시별·단기 클라이언트 인증서를 넣습니다. 아카이브를 읽고 쓸 수 있는 IAM 권한과 KMS 키가 실제 보호 경계입니다(4절).
  3. 보안 그룹에서 xDS 연결과 ELB를 거친 요청이 구분되나요? 구분되지 않습니다. 두 연결 모두 같은 프록시의 같은 보안 그룹에서 나갑니다. 라우트가 xds_cluster를 가리키면 외부 요청이 프록시의 인증서를 단 채 xDS 서버에 도착하므로 mTLS로도 막히지 않습니다. 보안 그룹, 라우트 검증, 프록시별 인가를 함께 둡니다(5절).

1. 왜 아카이브의 인증서인가

Kubernetes 사이드카와 ELB for Envoy는 첫 신원을 얻는 방법이 다릅니다.

항목Istio 사이드카 (Kubernetes)ELB for Envoy
첫 자격 증명Pod의 프로젝티드 서비스 계정 토큰없음. 아카이브로 전달
인증서 발급Istio 에이전트가 istiod에 CSR을 보내 워크로드 인증서를 받음옆에 에이전트를 띄울 수 없음. 고객 파이프라인이 발급해 아카이브에 넣음
인증서 공급에이전트의 로컬 SDS아카이브 파일을 watched_directory 파일 SDS로 읽음
노드 신원에이전트가 Pod 정보로 채움node.id는 AWS가 인스턴스 ID로 채우고, 고객은 node.cluster만 지정(생략하면 프록시 이름). CLI 플래그도 지정할 수 없음
신원의 뿌리Kubernetes API와 서비스 계정아카이브를 쓸 수 있는 IAM 주체와 KMS 키

AWS 문서는 xDS 인증 방식을 따로 정하지 않습니다. 다만 제어 플레인 주소와 TLS 인증서를 재시작 없이 바꾸려면 아카이브 파일을 watched_directory로 읽거나 제어 플레인이 직접 내려 주라고 안내합니다. AWS의 EKS 통합(elb-envoy-remote-infra-provider v1.0.0, 통합 API는 v1alpha1)은 Envoy Gateway 접속용 클라이언트 인증서·키·CA와 Envoy Gateway Pod IP를 아카이브에 넣고, 프록시가 그 IP의 18000 포트로 mTLS 연결합니다. 이때 클러스터의 모든 프록시가 같은 인증서와 키를 받으므로, 인증서만으로는 프록시를 구분할 수 없습니다. 이 가이드는 여기에 프록시별 인증서와 서버 쪽 인가를 더하는 구성을 권합니다.

2. 아카이브에 무엇을 넣을까

증명 수단판단이유
프록시별 클라이언트 인증서 + mTLS권장개인 키가 네트워크로 전송되지 않는 소유 증명입니다. SAN에 프록시 이름을 담아 서버가 인가에 씁니다. 만료가 인증서에 들어 있어 짧은 수명으로 피해 범위를 줄일 수 있습니다.
모든 프록시가 공유하는 인증서주의인증은 되지만 인증서만으로는 프록시를 구분할 수 없습니다. 서버가 node 값을 믿으면, 인증서가 하나 새는 순간 다른 게이트웨이의 설정도 요청할 수 있게 됩니다. EKS 통합은 클러스터의 모든 프록시에 같은 인증서를 넣습니다.
정적 토큰 + gRPC initial_metadata비권장스트림을 열 때마다 서버로 보내는 bearer 값입니다. 서버 로그나 중간 구간에서 새면 누구나 재사용합니다. 만료와 사용 범위를 따로 만들어야 하고, TLS가 없으면 평문입니다.
프록시 IAM 역할(roleArn)문서화된 방법 없음ELB for Envoy 문서에서 xDS 연결을 프록시 역할로 인증하는 방법은 찾지 못했습니다. 프록시 역할은 로그 전송과 Envoy 필터가 AWS 서비스를 호출할 때 쓰는 권한입니다.

인증서 발급 규칙 (예시)

  • 프록시마다 따로 발급하고, URI SAN을 spiffe://<trust-domain>/elb-proxy/<프록시 이름> 형태로 둡니다. bootstrap의 node.cluster에는 같은 프록시 이름을 넣습니다. 생략해도 기본값이 프록시 이름입니다.
  • EKU는 clientAuth만 둡니다. 백엔드용 업스트림 TLS 인증서와는 따로 발급합니다.
  • xDS 서버 인증서는 다른 CA로 발급하고, 프록시가 match_typed_subject_alt_names로 서버 이름(예: xds.example.test)까지 확인합니다. Envoy는 SAN 매처가 없으면 신뢰하는 CA가 서명한 인증서를 이름과 관계없이 받아들입니다.
  • 수명은 교체 파이프라인이 감당할 수 있는 만큼 짧게 둡니다(예: 7일 수명, 5일마다 교체). AWS Private CA 등으로 발급하고 만료 경보를 둡니다.

아카이브 구성과 bootstrap

아카이브는 Envoy가 보는 파일시스템 루트에 풀립니다. ZIP 안에 xds-auth/ 디렉터리를 두면 Envoy는 /xds-auth/…로 읽습니다.

bootstrap에는 ELB for Envoy가 받는 필드(node.cluster, dynamic_resources, static_resources 등)만 씁니다. 전체 파일은 xds-auth-bootstrap.yaml에 있습니다.

    transport_socket:
      name: envoy.transport_sockets.tls
      typed_config:
        "@type": type.googleapis.com/envoy.extensions.transport_sockets.tls.v3.UpstreamTlsContext
        sni: xds.example.test
        common_tls_context:
          tls_certificate_sds_secret_configs:
          - name: xds_client
            sds_config:

3. xDS 서버의 인가 규칙

node.cluster와 node.id는 프록시가 스스로 보내는 값입니다. 인증 근거로 쓰지 말고 인증서 SAN과 짝지어 확인합니다.

  • TLS에서 클라이언트 인증서를 필수로 요구하고, 프록시용 CA로만 검증합니다.
  • 스트림이 열리면 peer 인증서의 URI SAN을 기록하고, 스트림이 닫히면 지웁니다.
  • node가 실린 모든 요청에서 node.cluster가 SAN의 프록시 이름과 같은지 확인하고, 다르면 PermissionDenied로 스트림을 닫습니다. 첫 메시지만 확인하면 안 됩니다. go-control-plane은 이후 메시지에 node가 오면 그 값으로 바꿉니다(pkg/server/sotw/v3/ads.go:66-70, v0.14.0).
  • Delta xDS도 막습니다. ADS gRPC 서비스를 등록하면 SotW(StreamAggregatedResources)와 함께 Delta(DeltaAggregatedResources)도 열립니다. go-control-plane v0.14.0은 Delta 콜백이 없으면 Delta 요청을 허용합니다(pkg/server/v3/server.go:136-141). bootstrap이 SotW(api_type: GRPC)라면 서버에서 Delta를 거부하고, Delta를 쓴다면 Delta 콜백에도 같은 검사를 넣습니다.
  • 스냅샷은 node.cluster 기준으로 나누어, 인가된 프록시는 자기 게이트웨이의 리소스만 받게 합니다.
  • SDS로 백엔드 개인 키까지 내려 준다면, 그 키도 같은 인가 범위 안에 있어야 합니다.
// go-control-plane v0.14.0 serverv3.CallbackFuncs 요약 (전체: xds-auth-server.go)
const sanPrefix = "spiffe://example.test/elb-proxy/"
var mu sync.Mutex
peers := map[int64]string{}

cb := serverv3.CallbackFuncs{
    // Delta ADS는 쓰지 않으므로 거부한다. 콜백이 없으면 go-control-plane은 Delta 요청을 허용한다.
    DeltaStreamOpenFunc: func(context.Context, int64, string) error {
        return status.Error(codes.Unimplemented, "delta xDS disabled")
    },
    StreamOpenFunc: func(ctx context.Context, id int64, _ string) error {
        san := ""
        if p, ok := peer.FromContext(ctx); ok {
            if ti, ok := p.AuthInfo.(credentials.TLSInfo); ok &&
                len(ti.State.PeerCertificates) > 0 && len(ti.State.PeerCertificates[0].URIs) > 0 {
                san = ti.State.PeerCertificates[0].URIs[0].String()
            }
        }
        mu.Lock(); peers[id] = san; mu.Unlock()
        return nil
    },
    StreamClosedFunc: func(id int64, _ *core.Node) {
        mu.Lock(); delete(peers, id); mu.Unlock()
    },
    StreamRequestFunc: func(id int64, req *discovery.DiscoveryRequest) error {
        n := req.GetNode()
        if n == nil { return nil }                 // set_node_on_first_message_only
        mu.Lock(); san := peers[id]; mu.Unlock()
        if !strings.HasPrefix(san, sanPrefix) || n.GetCluster() != strings.TrimPrefix(san, sanPrefix) {
            return status.Errorf(codes.PermissionDenied, "node.cluster %q not allowed for %q", n.GetCluster(), san)
        }
        return nil
    },
}

전체 코드: xds-auth-server.go

4. 아카이브를 지키는 IAM과 KMS

관리형 프록시에서는 아카이브를 쓰는 주체가 프록시의 신원을 정하고, 아카이브를 읽는 주체가 개인 키를 얻습니다. 아래 액션은 모두 elasticloadbalancing: 접두사를 씁니다.

IAM 액션의미권장
CreateProxy
UpdateProxyConfiguration		프록시가 쓸 인증서와 xDS 주소를 정합니다.배포 파이프라인 역할만 허용합니다.
UpdateProxyNetworkConfiguration보안 그룹 등 프록시의 네트워크 설정을 바꿉니다.배포 파이프라인 역할만 허용합니다.
GetProxyConfigurationContentsincludeConfigArchive로 아카이브 내용, 즉 개인 키를 돌려줍니다. GetProxy와 분리돼 있습니다.배포 역할만 허용합니다. 조건 키는 aws:ResourceTag/${TagKey}뿐이라, 설정 파일만 읽게 하고 아카이브는 막는 구분은 IAM으로 할 수 없습니다. 감사에는 CloudTrail 기록을 씁니다.
GetProxy메타데이터만 돌려줍니다.운영자 조회용으로 허용합니다.
읽기 전용 정책에 들어 있습니다. AWS 관리형 정책 ElasticLoadBalancingReadOnly(v3, 2026-11-27 확인)는 elasticloadbalancing:Get*를 허용하므로 GetProxyConfigurationContents도 허용합니다(IAM 정책 시뮬레이터 결과 allowed, UpdateProxyConfiguration은 implicitDeny). ReadOnlyAccess는 ELB에 Describe*만 허용해 포함하지 않습니다. 기본값인 AWS 소유 키에서는 KMS가 이 읽기를 막지 않습니다.

고객 관리형 KMS 키를 쓰는 편이 좋습니다. 아카이브는 항상 저장 시 암호화됩니다. 고객 관리형 키를 지정하면 다음을 얻습니다.

  • GetProxyConfigurationContents 호출에 호출자의 kms:Decrypt도 필요해집니다. 키 권한이 없는 읽기 전용 역할은 여기서 걸러집니다.
  • 데이터 키가 암호화 컨텍스트 aws:elasticloadbalancing:proxy-arn에 묶여, 다른 프록시의 설정은 복호화되지 않습니다. 키 정책이나 IAM 정책에 kms:EncryptionContext:aws:elasticloadbalancing:proxy-arn 조건을 넣으면 역할마다 복호화할 수 있는 프록시를 제한할 수 있습니다.
  • CloudTrail로 키 사용을 감사할 수 있습니다.

단, 키 정책이 계정 root에 kms:*를 위임하면(AWS 예시 키 정책의 기본 형태) IAM으로 kms:Decrypt를 가진 관리자 역할은 여전히 읽을 수 있습니다. 그래서 키 사용 여부와 관계없이 SCP나 권한 경계에 명시적 Deny를 함께 두면, 실수로 붙은 Get* 권한까지 막을 수 있습니다. 아래는 Statement 예시이며, SCP는 관리 계정에는 적용되지 않습니다.

{
  "Sid": "OnlyDeployRolesReadProxyArchive",
  "Effect": "Deny",
  "Action": "elasticloadbalancing:GetProxyConfigurationContents",
  "Resource": "*",
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalArn": [
        "arn:aws:iam::111122223333:role/proxy-deploy",
        "arn:aws:iam::111122223333:role/proxy-breakglass"
      ]
    }
  }
}

5. 보안 그룹으로 구분되는가

AWS 문서에 따르면 프록시의 보안 그룹 규칙은 프록시로 들어오는 트래픽과 프록시가 보내는 트래픽을 모두 제어합니다. 보안 그룹은 프록시 단위로 지정하므로, xDS 연결과 백엔드로 가는 연결의 출발지는 같은 보안 그룹이고 Envoy 클러스터마다 출발지를 나눌 수 없습니다. EKS 통합도 공유 백엔드 SG 하나를 출발지로 삼아 노드 SG에 TCP 18000(xDS), 18002(Wasm), 각 백엔드 포트를 엽니다.

그래서 경계를 세 겹으로 둡니다

  1. 네트워크: xDS 서버 SG는 프록시 SG에서 오는 xDS 포트(필요하면 Wasm 포트)만 받습니다. xDS 서버를 다른 백엔드와 같은 SG·포트에 두지 않습니다.
  2. 라우트 검증: 배포 파이프라인에서 라우트가 참조하는 클러스터를 검사합니다.
    • xds_cluster처럼 제어 플레인용 이름을 막습니다.
    • admin 주소(127.0.0.1)를 가리키는 클러스터는 꼭 필요한 경로만 둡니다. AWS 문서는 /config_dump가 설정 속 비밀 값을 드러낼 수 있다고 경고합니다.
    • 목적지를 요청이 정하는 dynamic_forward_proxy·ORIGINAL_DST 클러스터는 쓰지 않습니다.
    • 백엔드용 업스트림 TLS에 xDS 클라이언트 인증서를 재사용하지 않습니다.
    • Gateway API라면 Envoy Gateway Pod·Service를 가리키는 backendRefs를 정책으로 막습니다.
  3. 프록시별 인가: 라우트 실수가 생겨도 호출자가 받는 것은 그 프록시 자신의 설정까지입니다(6절 재현). 공유 인증서를 쓰고 서버가 node 값을 믿으면 이 범위가 모든 게이트웨이로 넓어집니다.

보조 신호도 있습니다. 재현에서 Envoy 자신의 ADS 스트림에는 x-envoy-internal·x-forwarded-for가, 라우트를 거친 스트림에는 x-forwarded-proto·x-request-id가 실렸습니다. 서버가 x-request-id가 있는 스트림을 거부할 수도 있지만, 이 헤더는 HTTP 연결 관리자 설정에 따라 달라지므로 경계가 아니라 탐지 신호로만 씁니다.

7. 인증서 교체 절차

  1. 새 클라이언트 인증서를 발급합니다. 같은 CA면 서버 설정은 그대로입니다. CA를 바꾼다면 먼저 xDS 서버가 이전 CA와 새 CA를 함께 신뢰하게 합니다.
  2. 새 인증서를 넣은 아카이브로 UpdateProxyConfiguration을 호출하되 아카이브만 바꿉니다. AWS 문서에 따르면 아카이브만 바꾸면 Envoy가 재시작하지 않고, bootstrap까지 바꾸면 hot restart와 60초 drain이 일어납니다.
  3. 새 인증서는 다음 연결부터 쓰입니다. 오래 열린 ADS 스트림도 다시 연결되게 하려면 gRPC 서버의 keepalive.ServerParameters에 MaxConnectionAge와 MaxConnectionAgeGrace를 함께 둡니다(예: 12시간 + 5분). grpc-go에서 MaxConnectionAgeGrace의 기본값은 무한대여서 MaxConnectionAge만으로는 열린 스트림이 닫히지 않습니다.
  4. xDS 서버 로그에서 각 프록시의 새 일련번호를 확인한 뒤, 이전 인증서를 폐기하거나 이전 CA 신뢰를 제거합니다.

8. 점검 목록

  • xDS 연결에 mTLS를 쓰고, 프록시가 서버 CA와 서버 SAN을 검증한다.
  • 클라이언트 인증서를 프록시별로 발급하고, SAN과 node.cluster를 짝지어 모든 요청에서 인가한다.
  • Delta xDS를 쓰지 않으면 서버에서 거부하고, 쓴다면 Delta에도 같은 인가를 건다.
  • 정적 bearer 토큰에 의존하지 않는다.
  • GetProxyConfigurationContents를 배포 역할로 제한하고, ElasticLoadBalancingReadOnly처럼 Get*를 가진 역할을 점검한다.
  • 고객 관리형 KMS 키로 설정을 암호화하고, 키 정책과 명시적 Deny로 복호화·조회 주체를 제한한다.
  • xDS 서버 SG는 프록시 SG의 xDS 포트만 받는다.
  • 라우트가 xds_cluster, admin 주소, 제어 플레인 주소를 가리키지 못하게 파이프라인에서 검사한다.
  • 인증서 수명·교체 주기·만료 경보를 두고, 서버에 MaxConnectionAge와 MaxConnectionAgeGrace를 둔다.

검증 범위

로컬 재현으로 확인한 것은 mTLS 인증, SAN 인가, Delta 거부, 라우트 경유 접근, 파일 SDS 교체입니다. 보안 그룹 동작과 관리형 프록시에서의 인증서 교체는 측정하지 않았고, AWS 문서와 elb-envoy-remote-infra-provider v1.0.0 문서를 근거로 했습니다. 관리형 프록시에서 아카이브만 바꿀 때 재시작 없이 파일이 교체되는 동작은 상세 글의 관리형 프록시 xDS 파일 교체 실측(도쿄 리전)으로 확인했습니다. Envoy Gateway가 node별로 인가하는지는 확인하지 않았습니다.
